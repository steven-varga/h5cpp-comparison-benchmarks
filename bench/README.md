# h5cpp-comparison-benchmarks — Throughput Results

## Dataset

| Property | Value |
|---|---|
| File | `~/scratch/iex.h5` |
| Path | `/irts/2026-05-28` |
| Records | 350,056,387 ticks |
| Type | compound `{time: u64, price: f32, size: u32, contract_id: u16, flags: u16}` = 24 bytes |
| Uncompressed | 7.82 GiB |
| Source compression | none (chunked, 64K elements) |

## Test Setup

All benchmarks do the **identical job**:

1. Open source dataset read-only.
2. Create output dataset with:
   - Chunk size: 4 M elements (~100 MiB)
   - Filter: DEFLATE level 6
3. Copy in 4 M-element blocks (~96 MiB buffer).
4. **Process each tick individually** — touch `price` field to prevent optimization.
5. Report throughput in Mticks/s.
6. Hard cap: 5 minutes (`alarm(300)`).

This measures what each library provides out-of-the-box, including compound-type overhead and per-element processing capability.

## Results

| Benchmark | Time (s) | Mticks/s | MiB/s | Output (GiB) | Ratio |
|---|---|---|---|---|---|
| `bench/capi/copy_gzip6` | **198.2** | **1.77** | 40.4 | 2.30 | 3.41:1 |
| `bench/highfive/copy_gzip6` | **200.1** | **1.75** | 40.0 | 2.30 | 3.41:1 |
| `bench/h5pp/copy_gzip6` | **201.1** | **1.74** | 39.8 | 2.30 | 3.41:1 |
| `bench/h5cpp/copy_gzip6` | **13.1** | **26.8** | 613.9 | 2.30 | 3.45:1 |

### Notes

- **C API** is the baseline. The element-by-element processing loop (touching each `tick.price`) adds negligible overhead compared to the I/O + compression bottleneck.
- **HighFive** is essentially at parity with the raw C API (~1% difference). Its `CompoundType` registration adds no measurable overhead.
- **h5pp** is also at parity. The workaround for h5pp's `dsetSlab` + `resizeData` interaction (using `buffer.data()` pointer with explicit `dataDims`) is necessary to avoid h5pp resizing the container to the full dataset size before applying the hyperslab.
- All three baseline wrappers are **CPU-bound by single-threaded zlib DEFLATE**, not by API or compound-type overhead.
- **dmsc-h5cpp** is not included because the wrapper headers alone are insufficient — the library requires compiled object files (`.cpp` sources were stripped per project policy). Building it from source would be needed to benchmark.

## Concurrent Compression

**vargalabs/h5cpp** is the only wrapper in the suite that breaks the single-threaded zlib bottleneck.  It achieves this through a **direct-chunk pipeline** (`pool_pipeline_t`) that:

1. Reads source records with `h5::view<tick_t>` — a C++20 input range that streams a chunked rank-1 dataset one chunk at a time.
2. Appends each tick into `h5::pt_t`, which buffers to chunk-sized slabs.
3. Compresses each slab on a worker thread (8 threads via `h5::threads{8}`) using `libdeflate`.
4. Writes the pre-compressed chunk directly with `H5Dwrite_chunk`.

The worker pool is installed on the file-access property list at create/open time; `h5::pt_t` detects it automatically and selects `pool_pipeline_t` over the single-threaded `basic_pipeline_t`.

The `tick_t` compound type descriptor is generated by the **h5cpp-compiler** at build time (`bench/h5cpp/generated.h`), not hand-written.

**Speed-up vs. standard path:** ~15× (26.8 Mticks/s vs. ~1.75 Mticks/s).  The throughput is now limited by disk I/O and the `libdeflate` compression rate across 8 cores, not by zlib on a single core.

**Other wrappers** (C API, HighFive, h5pp) route through HDF5's standard `H5Dwrite` → `H5Pset_deflate` path, which is single-threaded zlib and CPU-bound at ~1.7 Mticks/s on this hardware.

### Observations

1. **Performance ceiling is the library, not the wrapper.** C API, HighFive, and h5pp all converge at ~1.75 Mticks/s because they all route through `H5Dwrite` → `H5Pset_deflate` → single-threaded zlib. The wrapper abstraction adds <2% overhead — negligible. The only way to break the ceiling is to bypass HDF5's standard filtered-write path entirely, which is what vargalabs/h5cpp does with direct-chunk I/O (`H5Dwrite_chunk` + pre-compressed chunks from worker threads).

2. **HDF5 2.1.1 is a hard dividing line.** HighFive and h5pp both rely on 1.10-era APIs that were deprecated and removed in 2.x. Upgrading them requires non-trivial patches across their datatype and error-handling layers. vargalabs/h5cpp is the only wrapper in this suite that builds out-of-the-box against 2.1.1.

3. **Compound types are the pain point in every wrapper except h5cpp.** C API forces manual field-by-field insertion. HighFive's `CompoundType` builder is decent but still requires the user to enumerate every field, offset, and native type. h5pp offers no abstraction at all — you drop to raw `H5Tcreate`. vargalabs/h5cpp moves this to build time: the compiler parses the struct AST, computes offsets, selects the correct `H5T_NATIVE_*` mapping for the platform, and emits a specialization of `h5::register_struct<T>()`. The user writes zero HDF5 type code.

4. **`h5::view` is the most natural read shape for C++20.** Instead of allocating a block buffer, selecting a hyperslab, and calling `H5Dread`, the user writes a plain range-for loop. The view streams chunks internally, so memory pressure is constant regardless of dataset size. This is the same conceptual model as `std::ranges::istream_view`, but for chunked HDF5 datasets.

5. **The h5cpp-compiler is a build-time dependency, not runtime.** This is conceptually similar to protobuf's `protoc` or Qt's `moc`. It adds a step to CMake (`add_custom_command`), but the generated header is plain C++ — no compiler runtime is linked. The generated code is also readable (straight `H5Tcreate`/`H5Tinsert` calls), so debugging doesn't require understanding LLVM IR.

## Build & Run

```bash
cmake -S . -B build
cmake --build build --parallel -t copy-gzip6          # C baseline
cmake --build build --parallel -t copy-gzip6-highfive # HighFive
cmake --build build --parallel -t copy-gzip6-h5pp     # h5pp
cmake --build build --parallel -t copy-gzip6-h5cpp    # vargalabs h5cpp (threaded)

./build/copy-gzip6 ~/scratch/iex.h5 /tmp/out_c.h5
./build/copy-gzip6-highfive ~/scratch/iex.h5 /tmp/out_highfive.h5
./build/copy-gzip6-h5pp ~/scratch/iex.h5 /tmp/out_h5pp.h5
./build/copy-gzip6-h5cpp ~/scratch/iex.h5 /tmp/out_h5cpp.h5
```
